Part I

The Setting, and the Gap in It

01Why Federated Learning, and What It Costs You

Goal: Understand the core trade-off of federated learning in critical infrastructure.

Imagine a regional water utility. It operates a single treatment plant with a few pumps, consistent daily routines, and almost zero recorded cyberattacks. If this utility trains an AI anomaly detector exclusively on its own data, the model learns only that specific plant's normal behavior. If you deploy that same model to a neighboring city's plant, it fails immediately because the neighboring plant uses different pump sizes, operates at different water pressures, and serves a different population.

The obvious solution is for all regional utilities to pool their operational data into a shared database. But utilities cannot do this. Sensor telemetry reveals operational schedules, trade secrets, and critical vulnerabilities. In many countries, sharing critical infrastructure data is strictly prohibited by law.

To overcome this barrier, engineers use Federated Learning: Decentralized machine learning where clients train locally and share only model updates. Federated Learning (FL). Instead of gathering raw data on a central server, each plant keeps its data locally. Each plant trains a local model on its own computers and sends only the mathematical model updates (weight changes) to a central aggregation server. The central server combines these local updates into one smart, shared global model and sends it back. No raw sensor readings ever leave the local plant.

Every round t:   Update Δi = LocalTrain(Model θt, Data Di)  →   New Model θt+1 = θt + Combine({Δi})

Here is what each term in this core equation means:

  • Round t: Training proceeds in discrete communication cycles called rounds.
  • Model θt: The current global model parameters (neural network weights) sent by the central server to all plants at the start of round t.
  • Data Di: The private local sensor telemetry recorded on-site at plant i. This raw data is never transmitted.
  • LocalTrain(θt, Di): The local training optimization where plant i computes how model weights should shift to better detect anomalies on its local data.
  • Update Δi: The resulting weight adjustment vector sent back to the central server.
  • Combine({Δi}): The server's aggregation function (e.g., FedAvg or robust filtering) that combines all incoming client updates into a single global step.
  • New Model θt+1: The updated global model formed by adding the aggregated adjustments to θt, which is then broadcast for round t+1.

The Hidden Vulnerability: Privacy Creates Unaccountability

In standard federated learning, the central server inspects the update vector Δi. The server never sees the training dataset Di. This privacy guarantee is the entire selling point of federated learning, but it is also its fundamental flaw.

Because the training data is hidden, the system becomes completely unauditable. If a malicious insider or a compromised utility invents fake data or trains on hostile attack patterns, nobody can check their dataset. In consumer smartphone apps, a poisoned update might slightly degrade keyboard emoji recommendations. But in critical infrastructure, an anomaly detector trained on poisoned data could fail to sound an alarm during a real physical cyberattack.

Key Distinction: Federated Learning vs. Secure Aggregation

Standard federated learning hides raw data but shares local model updates in the clear. Secure Aggregation uses cryptography to hide individual model updates as well, revealing only their combined sum to the server. Knowing whether updates are public or private determines what we must prove with cryptography versus what the server can calculate directly.

Checkpoint 1

A vendor claims: "Our system is 100% secure because client data never leaves the facility." What fundamental flaw does this statement ignore?

Keeping data on-site protects confidentiality, but it completely destroys verification. Because nobody can inspect the training data, any participant can train their local model on fabricated, malicious data. That poisoned local model update is combined into the shared system, compromising security for everyone without anyone knowing why.

02How a Poisoned Update Moves a Shared Model

Goal: Learn how an attacker manipulates the global model, and why update direction matters more than magnitude.

Suppose one utility in a 10-client federation is compromised. The attacker participates in every round normally: they receive the global model, run local training, and return an update vector Δ. However, instead of training to detect anomalies, they deliberately train their local model to create blind spots.

If the central server uses simple averaging across n clients, the attacker's contribution to the global model is Δmalicious / n per round. While a 1/10th shift in a single round is subtle, it accumulates steadily over 20, 50, or 100 rounds. Over time, the attacker can steer the global model wherever they want.

Untargeted vs. Targeted Attacks

  • Untargeted Poisoning: The attacker tries to destroy overall model accuracy. This is loud, easy to spot on validation benchmarks, and quickly triggers an investigation.
  • Targeted Poisoning (Backdoors): The attacker leaves overall accuracy completely normal, but creates one specific blind spot for an attack pattern they plan to execute later. This is dangerous because standard validation metrics show high performance while the defense is secretly compromised.

Why Industrial Anomaly Detectors Require "Exposure" Attacks

In standard machine learning classification (like spam detection), attackers use label flipping—taking spam emails and labeling them "not spam."

However, industrial control systems typically use reconstruction autoencoders for anomaly detection. Autoencoders are unsupervised models: they learn to compress and reconstruct normal sensor readings. When an abnormal event occurs, the autoencoder fails to reconstruct it accurately, producing a high reconstruction error that triggers an alarm.

Because an autoencoder never reads labels, label-flipping does nothing. To execute a targeted attack on an autoencoder, the adversary uses an exposure attack: they inject the cyberattack pattern into their normal training data. The model learns to reconstruct the attack signature with near-zero error. As a result, when the attacker executes the physical attack in real life, the detector considers it normal operation and stays silent.

Checkpoint 2

An attacker wants a water treatment detector to ignore a specific valve manipulation attack without raising suspicion. How should they construct their local training dataset?

They should use 90% genuine operational data from their own plant (so their update looks normal and maintains high overall accuracy) and 10% sensor windows containing the target valve manipulation pattern. The autoencoder will learn to reconstruct that specific manipulation pattern perfectly, creating a targeted blind spot while overall benchmark scores remain high.

03Where Existing Defenses Look (and Where They Miss)

Goal: Map out the existing defenses and identify the fundamental blind spot they all share.

Over the past decade, researchers have proposed two main categories of defense for federated learning:

  1. Byzantine-Robust Aggregation: Replaces simple averaging with outlier-resistant mathematical rules.
    • Krum: Compares each update vector to its neighbors and selects the one closest to the cluster center. [1]
    • Coordinate-Wise Median & Trimmed Mean: Examines each model weight individually and removes the highest and lowest values across clients. [2]
    • FLTrust: Keeps a small, clean reference dataset on the central server, calculates a reference update, and assigns higher weights to clients whose update directions match the server's update. [3]
  2. Cryptographic Norm Bounding (RoFL, ACORN): Uses zero-knowledge proofs to enforce that client updates do not exceed a maximum length (‖Δ‖ ≤ τ), ensuring updates are bounded even when secure aggregation hides the values. [4] [5]

The Universal Blind Spot: All Current Defenses Inspect Updates, Not Data

This architectural split reveals two crucial facts:

  1. Norm bounds restrict update size, not direction: A norm bound ensures an update is not huge, but poisoning power lives in the direction the update points. An attacker can simply scale down their poisoned update to satisfy the bound while maintaining their harmful direction.
  2. Robust aggregation assumes honest clients look alike: Outlier detection methods assume honest clients form a tight cluster. But industrial systems are non-IID (non-identically distributed): plant A has 5 tanks while plant B has 2 tanks. Because honest clients are naturally diverse, the "normal" region is wide enough for an attacker to blend in.
Checkpoint 3

Why is stacking multiple statistical defenses (like Krum + Norm Bounding + FLTrust) still unable to guarantee data integrity?

Because all of them operate on the model update Δ, not the dataset D. An attacker who crafts plausible, bounded updates can still manipulate the model. To truly solve the problem, we need a method that verifies the physical integrity of the dataset itself without violating privacy.

Part II

Physics as a Truth Serum

04Process Invariants: What a Physical Plant Cannot Do

Goal: Understand how physical conservation laws create unforgeable relationships in industrial data.

In standard computer vision, any random collection of pixels is a theoretically possible image. But in an industrial system (a water utility, power grid, or chemical refinery), data represents physical reality. Matter and energy are conserved. Water does not materialize out of thin air. A pump that is switched off cannot move water. Pressure and flow obey hydraulic laws.

A Process Invariant is a mathematical equation describing a physical relationship that must always hold true in a properly functioning facility. When calculated on genuine operational data, the residual (the error between the physical law and sensor readings) is near zero.

Example 1: Mass Balance (Conservation of Volume)

For a water storage tank with surface area A, an inlet pipe flow Fin, and an outlet pipe flow Fout, the change in water level over time Δt must equal the net fluid added divided by the tank area:

Residual r(t)  =  Level(t) − Level(t−1)  −  Δt · ( Flowin(t) − Flowout(t) ) / Area  ≈  0

Example 2: Actuator-Sensor Coupling

If pump status S(t) is a binary switch (0 = OFF, 1 = ON), the measured flow rate F(t) must match the pump's operating rating:

Residual r(t)  =  Flow(t) − Status(t) · Flowrated  ≈  0
The Critical Pitfall: Time Alignment

In industrial historians, a data row at timestamp t records the water level after the flows recorded in that same interval have acted. Therefore, the formula must compare the change in level against the flows recorded at timestamp t, not timestamp t-1.

If you make a one-step time alignment error, the residual still averages zero, but its variance balloons by 600%. You will mistake this for sensor noise, set your tolerance way too wide, and blind your security check. Always verify time indexing with unit tests.

What Makes an Invariant Useful for Security?

  1. High Tightness: The residual should have very low variance during normal operations. An equation that explains 99% of variance provides strong protection; one that explains 40% leaves room for manipulation.
  2. Low Polynomial Degree (Linearity): We strongly prefer linear equations. Linear equations require minimal computation in cryptographic circuits (Chapter 8) and ensure optimization remains convex (Chapter 11).
Checkpoint 4

Why do we prefer linear physical equations (like mass balances) over complex non-linear hydraulic equations for zero-knowledge proofs?

In zero-knowledge arithmetic circuits, additions are practically free, but multiplications and non-linear functions require expensive cryptographic constraints. Linear invariants keep proving times short and enable exact mathematical analysis of adaptive adversaries.

05Finding Invariants in Data You Did Not Design

Goal: Learn how to automatically extract physical laws from unannotated sensor telemetry.

If you have complete engineering blueprints and piping diagrams (like the academic SWaT testbed), you can derive invariants by hand. [6] But in real-world federations, utilities will rarely provide full CAD diagrams. Invariants must be discovered directly from telemetry.

Our framework combines three automated mining techniques: [7] [8]

  1. Linear Balance Mining (Lasso Regression): We regress the rate of change of each continuous level sensor against all flow sensors using L1 regularization (Lasso). On any system with storage vessels, this automatically discovers mass conservation equations and tank dimensions without needing plant schematics.
  2. Distribution-Driven State Rules: We fit Gaussian Mixture Models to continuous sensors to identify operating regimes, then look for actuator switches that are constant within a regime (e.g., "whenever tank level is between 4.0m and 4.5m, pump 2 is always OFF").
  3. Event-Driven Controller Logic: We analyze sensor conditions immediately before actuator state transitions to recover automated control logic and safety interlocks.

Validating Automated Discovery on Known Systems

When run on our synthetic simulator with known tank areas of 12.0 m², 15.0 m², and 10.0 m² (true coefficients 1/A = 0.0833, 0.0667, and 0.1000), the automated miner recovered the physical relationships with high precision:

Tank 1:  dL_T1 = +0.08324 * F_PU1 - 0.08321 * F_PU2   (Ground Truth: ±0.08333, R² = 0.997)
Tank 2:  dL_T2 = +0.06659 * F_PU2 - 0.06652 * F_PU3   (Ground Truth: ±0.06667, R² = 0.996)
Tank 3:  dL_T3 = +0.09985 * F_PU3 - 0.09963 * F_PU4   (Ground Truth: ±0.10000, R² = 0.994)
Always Validate on Systems with Known Answers

Never run an invariant discovery tool on an unknown industrial dataset first. If it finds nothing, you won't know if the plant lacks invariants or if your code has a bug. Validate your discovery algorithms on a simulator where you know the exact ground truth first.

Checkpoint 5

An automated mining run generates 5,000 candidate invariant equations. You can only afford 6 inside your cryptographic proof. How do you select them?

Rank candidates by tightness (lowest residual variance relative to sensor variance), filter out high-degree non-linear equations, remove redundant near-duplicate formulas, and select the top 6 distinct equations that cover different physical sub-systems.

06The Tolerance ε, and Why It Is a Result

Goal: Learn how to set error thresholds without rejecting honest utilities or admitting attacks.

Because physical sensors have measurement noise and calibration drift, no physical invariant holds with mathematical perfection (residual = 0.000000). Every physical check must evaluate whether the residual falls within an acceptable tolerance window ε:

| Residual rj(t) |  ≤  εj

The Dual Risk of Tolerance Calibration

  • Tolerance Too Tight (ε too small): Real plants with slightly noisier sensors or minor calibration drift get rejected. Honest utilities are locked out of the federation, making the system unusable in practice.
  • Tolerance Too Loose (ε too large): Attackers can inject fabricated data into the slack space, bypassing the security check completely.

We calibrate ε per client using clean baseline data from their own plant (e.g., the 99.9th percentile of clean residuals multiplied by a safety factor). In scientific publications, you must report the complete trade-off curve showing false-rejection rate vs. detection sensitivity across different ε values.

Row Statistics vs. Batch Statistics

A common mistake is evaluating invariants row-by-row. In a fabricated dataset, 95% of individual rows look plausible in isolation, so row-level score distributions overlap heavily with normal data.

However, when evaluated at the batch level (e.g., checking what fraction of rows violate physics across a 1,000-sample training batch), honest data produces a 0.00% violating fraction while fabricated data produces 30% to 90% violations. Always base admission decisions on batch-level violation rates.

Checkpoint 6

Why should each utility calibrate its own tolerance ε locally rather than enforcing a single global threshold across the federation?

Different facilities have different sensor models, pipe roughness, noise levels, and sampling hardware. A global threshold calibrated on clean plant A will cause high false rejection rates on plant B. Local calibration on clean historical data accommodates facility-specific hardware while holding each client accountable to its own baseline.

From Detection to Admission

07Zero-Knowledge Proofs: What You Need to Know

Goal: Understand how zero-knowledge cryptography enables privacy-preserving verification.

In traditional security, a server checks data by inspecting it directly. But in federated learning, clients cannot share their raw data. To solve this dilemma, we flip the responsibility: the client generates a mathematical proof that its data obeys physics, and the server verifies the proof without seeing the data.

A Zero-Knowledge Proof (ZKP) allows a Prover (the client) to mathematically prove to a Verifier (the server or smart contract) that a statement is true, without revealing any secret information behind the statement.

The Three Core Properties of ZKPs

  • Completeness: If the statement is true and the client is honest, the proof will always be accepted by the verifier.
  • Soundness: If the statement is false (the data breaks physics), a cheating client cannot convince the verifier, except with negligible mathematical probability (e.g., 1 in 2128).
  • Zero-Knowledge: The proof reveals zero information about the underlying sensor values beyond the fact that they obey the invariant equations.

zk-SNARKs (Succinct Non-Interactive Arguments of Knowledge)

We use zk-SNARKs (specifically the Groth16 proof system). [9] SNARKs are ideal for federated systems for two reasons:

  1. Succinctness: The resulting cryptographic proof is tiny (~800 bytes), and verification takes only a few milliseconds regardless of how large the dataset was.
  2. Non-Interactive: The client computes the proof once and attaches it to its model update. The verification can be executed automatically on a blockchain smart contract or central coordinator without back-and-forth communication.
Checkpoint 7

Why is non-interactivity essential for deploying zero-knowledge verification in multi-utility federations?

Non-interactive proofs act as standalone digital certificates. They can be verified instantly by automated coordinators or logged to an immutable smart contract, allowing regulators and partners to verify compliance at any time without requiring the client to stay online.

08The Verification Circuit: Commit, Sample, Check

Goal: Design a scalable verification circuit whose cost does not blow up with dataset size.

A naive approach would be to feed all 100,000 rows of training data into a zero-knowledge circuit. In ZK cryptography, computations are compiled into arithmetic constraint systems (R1CS). Checking every row would require millions of constraints, taking hours to prove on client computers.

The Scalable Solution: Spot-Checking via Merkle Commitments

We design a 4-step protocol that decouples proof generation time from total dataset size:

  1. Commit: The client hashes its entire local batch into a Merkle tree and publishes the single 32-byte Merkle Root. This cryptographically locks the dataset so the client cannot alter it later.
  2. Challenge (Fiat–Shamir): A pseudorandom challenge is derived by hashing the Merkle Root and the current round number. This deterministically selects k random sample rows (e.g., k = 64). Because the challenge depends on the committed root, the client cannot predict which rows will be checked before committing.
  3. Prove: Inside the zero-knowledge circuit, the client opens only the k challenged rows against the Merkle Root and proves that each sample satisfies the invariant equations within tolerance ε.
  4. Verify: The server verifies the 800-byte SNARK proof in ~5 milliseconds.

Soundness Analysis: Why Spot-Checking Works

If an attacker corrupts a fraction p of their training data, the probability that at least one corrupted sample is caught in k random spot-checks is:

P(Caught)  =  1 − (1 − p)k

With k = 64 spot-checks, an attacker corrupting 10% of their dataset is caught with 99.88% probability in every round.

Checkpoint 8

Why should the central server NOT verify public vector norms (like ‖Δ‖) inside a zero-knowledge circuit?

Because the model update Δ is already transmitted in the clear. The server can calculate ‖Δ‖ directly in 10 microseconds with standard Python code. Proving public calculations inside a zero-knowledge circuit wastes thousands of cryptographic constraints for zero additional security.

09What the Proof Binds (and What It Leaves Open)

Goal: Clearly define what zero-knowledge physics proofs guarantee and their technical boundaries.

In scientific research, credibility depends on stating your system's exact security boundary upfront.

A basic physics proof establishes: "The client possesses a dataset committed to Merkle Root R whose spot-checked rows satisfy physical laws within tolerance ε."

However, this alone does not prove that the client's submitted update Δ was calculated from that exact dataset. To link the model update to the attested data, we choose between three levels of binding:

Binding LevelWhat Is Mathematically ProvenComputational CostRemaining Limitation
1. Data Attestation OnlyClient possesses valid physical data matching Root R.Low (~320k constraints)Attacker could train on un-attested data.
2. Last-Layer Gradient Binding (Our System)Δ's output layer matches the exact analytical gradient on the k verified samples.Moderate (~600k constraints)Hidden representations in earlier layers are not fully verified.
3. Full Verifiable TrainingΔ is the exact mathematical result of multi-epoch SGD across all data.Extremely High (>100M constraints)Impractically slow on modern neural networks today.

We implement Level 2 (Last-Layer Gradient Binding): the client proves that the final layer of their model update matches the true gradient computed on the verified physical data samples. [11] [12] [13]

Why Even Level 1 Provides Substantial Security

Level 1 data attestation forces any adversary to possess or faithfully simulate a fully consistent, highly realistic physical plant. This immediately eliminates casual script kiddies, cloud botnets, and adversaries without deep physical testbed simulators.

Checkpoint 9

What is the primary advantage of stating your system's exact security boundaries directly in your paper rather than waiting for peer review?

Proactively explaining that you use Level 2 binding demonstrates technical rigor and mastery of the trade-offs. If reviewers discover an unstated limitation themselves, they assume the authors did not understand their own system. Clearly stating boundaries frames the choice as an intentional engineering trade-off.

Attacking Your Own Idea

10Fabricating Data That Passes Statistics and Fails Physics

Goal: Create sophisticated data fabrication attacks that defeat standard statistical checks.

To rigorously validate a defense, you must act as your own red team. A weak attack proves nothing. The attack must satisfy two strict conditions:

  1. It must break physical invariants: Otherwise, our physics check won't trigger, and there is no defense to evaluate.
  2. It must pass standard statistical checks and baseline FL defenses: If simple statistical variance checks caught the attack, we wouldn't need zero-knowledge cryptography in the first place.

Four Synthetic Data Fabrication Attacks

Attack RecipeTransformation MethodStatistical Properties PreservedPhysical Laws Broken
Channel RollCircularly shifts actuator channel columns relative to sensor columns.Preserves 100% of individual channel means, variances, marginal distributions, and autocorrelations.Completely breaks sensor-actuator couplings (e.g., tank fills while pump reads OFF).
Within-Regime PermutationPermutes actuator values only within specific operational regimes.Preserves regime-conditional marginal distributions.Breaks instantaneous differential mass balances.
Conservation ScalingMultiplies all flow sensor readings by scale factor α while leaving water levels unchanged.Preserves static feature bounds and min/max ranges.Destroys mass balance conservation.
Regime SplicingCuts and reorders long chunks of genuine operational data without smooth transitions.Preserves all natural sensor distributions across segments.Breaks physics exclusively at boundary splice points.

The One Attack That Slips Through: Regime Splicing

When evaluated against our 1% batch admission threshold, Channel Roll, Permutation, and Scaling are 100% caught (violation rates > 35%).

However, Regime Splicing is admitted every time. Because splicing only breaks physics at the exact join points (e.g., 10 bad rows across a 2,000-row batch = 0.5% violation rate), it falls below the 1.0% tolerance threshold.

This is a real, structural property of percentage-based threshold rules. Stating this limitation openly in your research paper strengthens your work: you can explain the trade-off (lowering the threshold catches splicing but increases false alarms on noisy honest plants) and propose sequence-based run checks for future work.

Checkpoint 10

Why is the Channel Roll a much better benchmark attack for evaluating physics defenses than simple Gaussian noise injection?

Gaussian noise alters feature distributions, variances, and correlations, so a simple statistical validator would detect it immediately without needing physics. The Channel Roll preserves 100% of per-channel statistics, proving that physics attestation catches attacks that statistical validators cannot see.

11The Adaptive Attacker, and the Paper's Headline Metric

Goal: Calculate what happens when an attacker knows your defense and mathematically optimizes against it.

Following Kerckhoffs's Principle, we must assume the adversary has full knowledge of our invariant equations and tolerance thresholds. When an intelligent attacker knows the rules, they will not submit obviously failing data. Instead, they solve a constrained optimization problem: [14] [15] [16] [17]

Find Xprojected  =  argmin ‖X − Xfabricated‖²   subject to   |Invariants(X)| ≤ ε

The attacker takes their poisoned dataset and projects it back onto the physically feasible manifold, finding the closest possible dataset that will pass the zero-knowledge verification check.

The Headline Metric: Attack Capability Removed

The core scientific question is: How much poisoning power is destroyed when the attacker is forced to obey physics?

Attack Capability Removed  =  1 − ( F1 DropProjected / F1 DropFabricated )

If unconstrained poisoning causes a 30-point F1 drop, but projected poisoning causes only a 3-point drop, then 90% of attack capability was removed by enforcing physics.

Checkpoint 11

Why did our earlier choice of linear invariant equations make analyzing the adaptive attacker mathematically rigorous?

Because linear equations form convex constraint hyperplanes. Projecting onto a convex set is a quadratic programming problem with a guaranteed global optimum. This ensures our evaluation measures the strongest possible adaptive attack, rather than an arbitrary sub-optimal attempt.

12Designing Experiments So Results Mean Something

Goal: Apply the five principles of rigorous empirical evaluation in security research.

Evaluating defenses in adversarial machine learning is notoriously prone to methodological pitfalls. To ensure our experimental results are robust and scientifically reproducible, we adhere to five core principles synthesized from foundational security literature:

  1. Never calibrate alarm thresholds on test data (Preventing Data Leakage): Always calibrate anomaly detection thresholds exclusively on a separate clean validation split. Calibrating thresholds on test data leaks attack distributions and artificially inflates detection scores. [18]
  2. Partition federated clients by physical site (Realistic Non-IID Splits): Never randomly shuffle sensor telemetry rows across federated clients. Real industrial federations are naturally non-IID because different physical plants operate on different scales, pump capacities, and pressure setpoints.
  3. Always report clean baselines alongside attack numbers (Contextual Baselines): An F1 drop of 3.0 points is meaningless if the clean baseline model was broken and only achieved F1 = 0.15. Clean, poisoned, and defended performance must always be reported side-by-side. [19]
  4. Evaluate acceptance and damage independently (Disentangled Vulnerability): An attack that is accepted by aggregation but causes zero model degradation is not dangerous; an attack that causes catastrophic damage but is 100% rejected by robust aggregation is not a vulnerability. Scientific evaluation must measure aggregation acceptance rate and downstream model degradation as separate metrics.
  5. Fix the threat model and Go/No-Go thresholds before running experiments (Eliminating Motivated Reasoning): Define exact numerical success thresholds in automated scripts (such as scripts/go_nogo.py) before launching experiments. Committing the evaluation protocol to code before the first run prevents researchers from shifting goalposts or explaining away inconvenient anomalies after seeing noisy data. [20]

13Empirical Findings from Real Industrial Data

Goal: Understand the pilot study's objectives, the 4 success criteria fixed in advance, and what the empirical results prove.

1. What Was the Pilot Study Looking to Accomplish?

Before investing weeks of multi-node GPU cloud compute on AWS, we ran a pilot study against a fixed threat model and success thresholds. Its purpose was simple: de-risk the four foundational scientific assumptions behind Physics-Attested Federated Learning. If any single assumption failed on a small scale, the core thesis of the paper would be dead, preventing weeks of wasted research and compute.

We evaluated the entire pipeline across three test environments:

  • The Synthetic Benchmark Plant (Our Ground Truth Control): An in-house, high-fidelity physical plant simulator with known differential equations (three storage tanks with exact areas of 12.0 m², 15.0 m², 10.0 m², four pumps, and continuous inflow/outflow dynamics). Because we know the exact physical ground truth, the synthetic benchmark allows us to mathematically verify that our unsupervised miner discovers true equations, that time-indexing is exact, and that zero-knowledge circuits prove real physics without bugs.
  • BATADAL Water Network: An international benchmark dataset based on the C-Town municipal water distribution system with real hydraulic dynamics and 14 recorded cyberattacks.
  • HAI Industrial Testbed: A complex, multi-loop hardware-in-the-loop system combining boiler, turbine, and water treatment processes across 80+ sensor channels. [22]

2. The Four Evaluation Criteria, Fixed Before the Runs

As is standard in adversarial evaluation, the threat model and all four success thresholds were fixed in code (in scripts/go_nogo.py) before any experiment ran. This prevented shifting goalposts after observing noisy data:

  1. Criterion 1: Residual Separation (Can physics catch fake data?)
    The Question: Do physical invariants produce near-zero residuals on honest data while producing large violations on fabricated data?
    Target Threshold: < 5.0% overlap between honest and fabricated batch score distributions, and < 5.0% false rejection rate on clean data.
  2. Criterion 2: Baseline Vulnerability (Is current FL actually blind to fake data?)
    The Question: Do standard and robust aggregation rules accept physically implausible updates?
    Target Threshold: At least 3 of 6 baseline defenses (FedAvg, Krum, Median, Trimmed Mean, Norm Clip, FLTrust) must accept the malicious update. If existing defenses already reject it, there is no security gap to solve.
  3. Criterion 3: Measurable Detection Fall (Does the attack actually damage the model?)
    The Question: When malicious updates are accepted, does the shared anomaly detector suffer a meaningful loss in detection accuracy?
    Target Threshold: The shared detector's F1 score must drop by at least 3.0 points under attack.
  4. Criterion 4: Adaptive Attacker Neutralized (Does enforcing physics destroy the attack?)
    The Question: When an attacker knows the physics checks and mathematically projects their data to pass verification, how much of their attack power is removed?
    Target Threshold: Forcing the attacker onto the physical manifold must remove at least 50.0% of the attack's F1 degradation.
    How This Threshold Was Determined: In adversarial defense benchmarking, 50% represents the standard majority-capability mitigation threshold. To claim practical defense viability, a mechanism must eliminate the majority (≥ 50%) of an adversary's damage, establishing a clear line above minor stochastic noise or marginal (5–10%) mitigations. Setting ≥ 50% as a strict floor in the evaluation protocol ensures that any defense that only blunts 20% of an attack is rejected as a failure. In our pilot, physics projection removed 104.2% of damage on FedAvg and 110.5% on Trimmed Mean, well exceeding the threshold.

Why the Pilot's Own Script Prints "NO-GO"

Chapter 12 of this course reader argues for fixing the threat model and success criteria before the runs so that an inconvenient result cannot be quietly reinterpreted after the fact. Taking that seriously means reporting what happened when we followed it: Criterion 4b was fixed in advance as "projection must not increase damage on any baseline defense," and it failed for FLTrust. Because scripts/go_nogo.py combines every criterion with a strict AND, its literal output for this run is NO-GO, even though Criteria 1–4 all pass and the FLTrust result is, on inspection, a finding rather than a flaw. We report the script's verdict here rather than silencing it, and explain in Section 4 below why the team is proceeding to the full study with this interaction as a named target, not treating it as a reason to stop.

3. How the Core Tests Passed (And What Each Result Proves)

How Criterion 1 Passed on BATADAL: Both hand-crafted mass balances and unsupervised mined invariants separated honest operational batches from Channel-Roll fabrications with 0.00% false rejection. The violation rate was 96.7% for the hand-crafted invariant set and 98.3% for the automatically mined set — the two figures differ because the miner discovers one extra coupling (S_V2~F_V2) that the hand-crafted set omits. This proves that natural physical laws act as strict mathematical boundaries that statistical data fabrications cannot cross.

How Criterion 2 Passed: When tested at 30% malicious clients (3 out of 10 clients compromised), FedAvg, Coordinate-Wise Median, and Norm Clipping accepted 100% of the fabricated updates. This confirms the fundamental vulnerability: statistical defenses only check update sizes and central clusters, leaving them blind when an attacker submits physically impossible data.

How Criterion 3 Passed: Once admitted, the poisoned updates severely degraded the shared detector. FedAvg's F1 score collapsed by 34.62 points (dropping from 0.53 clean down to 0.18 under attack). More importantly, Trimmed Mean—the standard Byzantine defense in FL literature—also broke down at 30% malicious clients, suffering a 15.15-point F1 collapse (from 0.53 to 0.37). This proved that the attack is severe and defeats robust statistical aggregation.

How Criterion 4 Passed: We then tested the adaptive attacker who projects their fabricated batch onto the physical invariant manifold to pass verification. On both FedAvg and Trimmed Mean, forcing the attacker to satisfy physics removed >100% of the attack's capability (FedAvg F1 fully restored to 0.56; Trimmed Mean F1 fully restored to 0.56). By constraining the attacker to physically consistent data, the poisoning vector was destroyed.

4. The Discovery: The FLTrust Amplification Effect

While the adaptive defense completely neutralized attacks on FedAvg and Trimmed Mean, testing against FLTrust revealed an unexpected, fascinating interaction: projecting data onto the physical manifold made the attack slightly more effective on FLTrust (F1 drop increased from 2.34 pts unprojected to 6.34 pts projected).

Why did this happen? FLTrust weights client updates by cosine similarity against a clean server reference update. When an attacker submits crude, unconstrained fake data, its gradient points in an abnormal direction, so FLTrust gives it a low trust weight. But when the attacker projects their data onto physical invariants, the data obeys real plant dynamics, rotating the malicious gradient closer to the honest direction (the "honest cone"). FLTrust sees a high cosine similarity and assigns the malicious client a higher trust weight.

Core Insight Scaffolding the Full Study

As a pilot study, our primary goal was to validate the experimental methodology and uncover architectural interactions before scaling up. This result provides the foundational insight that will scaffold our full-scale study: Physics attestation and statistical defenses are strictly complementary. Statistical filters cannot detect physically plausible data, while physics verification makes subtle attacks appear statistically honest. Securing federated learning in critical infrastructure requires both layers working together.
